Electiva Profesional I — Desarrollo de Aplicaciones Móviles

Sistema de Gestión de Inventario — API REST + Flutter

1. Objetivo

Desarrollar una solución informática para la gestión de inventario de productos de un establecimiento comercial, compuesta por una API REST propia con persistencia en base de datos y una aplicación móvil desarrollada en Flutter que consuma dicha API mediante el paquete Dio.

El ejercicio busca integrar los conocimientos trabajados durante el semestre relacionados con desarrollo móvil, peticiones HTTP, operaciones CRUD, programación asíncrona, navegación, organización de proyectos y consumo de servicios web.

2. Descripción general

La solución deberá estar compuesta por dos proyectos funcionales:

  1. Backend: API REST desarrollada con la tecnología de su preferencia (Laravel, Node.js, Python, entre otras), conectada a una base de datos que almacene permanentemente los productos.
  2. Frontend móvil: aplicación desarrollada en Flutter que permita consultar, registrar, editar y eliminar productos mediante peticiones HTTP realizadas a la API.

Importante: No se permitirá simular las operaciones CRUD mediante datos estáticos, listas locales o información que se pierda al reiniciar el sistema. Los datos deberán almacenarse y recuperarse desde una base de datos a través de la API desarrollada.

3. Backend — Desarrollo de la API REST

Deberan construir una API REST para administrar productos. La tecnología utilizada para su implementación será de libre elección.

3.1. Entidad Producto

La base de datos deberá contener, como mínimo, los siguientes campos:

Campo Tipo Descripción
id Entero Identificador único y autogenerado.
nombre Texto Nombre del producto.
codigo Texto Código único del producto.
descripcion Texto Descripción adicional (opcional).
precio Decimal Precio unitario del producto.
cantidad Entero Unidades disponibles.
categoria Texto Categoría del producto.

3.2. Endpoints obligatorios

La API deberá implementar, como mínimo, los siguientes cinco endpoints:

Método Endpoint Funcionalidad
GET /api/productos Listar todos los productos.
GET /api/productos/{id} Consultar el detalle de un producto.
POST /api/productos Registrar un nuevo producto.
PUT /api/productos/{id} Actualizar un producto existente.
DELETE /api/productos/{id} Eliminar un producto.

3.3. Requisitos del backend

  • Implementar una base de datos con persistencia real.
  • Retornar las respuestas de la API en formato JSON.
  • Implementar correctamente los métodos HTTP solicitados.
  • Validar campos obligatorios, código único, precios y cantidades válidas.
  • Utilizar códigos de respuesta HTTP apropiados (200, 201, 404, 422, entre otros).
  • Registrar al menos 10 productos de prueba para demostrar el funcionamiento.
  • Permitir que Flutter realice las operaciones directamente sobre los datos almacenados.

4. Frontend — Aplicación móvil Flutter

Desarrollar una aplicación móvil con una interfaz organizada, navegación funcional y consumo de la API mediante Dio.

4.1. Dashboard principal

La pantalla de inicio deberá incluir:

  • Nombre e identificación visual de la aplicación.
  • Menú de navegación para acceder a las funcionalidades.
  • Tarjeta con el total de productos registrados.
  • Tarjeta con el total de unidades disponibles en inventario.
  • Tarjeta con el valor económico total del inventario, calculado mediante la suma de precio × cantidad de cada producto.
  • Acceso a la gestión de productos.

Los indicadores deberán calcularse con información real proveniente de la API y actualizarse cuando se modifiquen los productos.

4.2. Gestión de productos — CRUD completo

  1. Listar: obtener los productos desde la API y mostrar nombre, precio y cantidad disponible.
  2. Consultar: visualizar el detalle completo de un producto seleccionado.
  3. Registrar: implementar un formulario que permita almacenar nuevos productos mediante una petición POST.
  4. Editar: permitir seleccionar un producto, precargar sus datos y actualizarlo mediante PUT.
  5. Eliminar: permitir eliminar un producto mediante DELETE, solicitando confirmación al usuario.

Después de registrar, actualizar o eliminar un producto, la interfaz deberá reflejar correctamente los cambios realizados.

4.3. Navegación e interfaz

  • Implementar navegación funcional mediante go_router.
  • Incluir un menú lateral o inferior para desplazarse entre las funcionalidades principales.
  • Utilizar componentes visuales de Flutter y mantener una presentación coherente.
  • Implementar formularios organizados con validación básica de entradas.
  • Mostrar mensajes claros cuando una operación se complete o falle.
  • Contemplar los estados de carga, error y ausencia de registros.

5. Requisitos técnicos y buenas prácticas

El proyecto Flutter deberá conservar la estructura, organización de archivos y separación de responsabilidades trabajadas durante las clases.

  • Utilizar obligatoriamente Dio para las peticiones HTTP.
  • Utilizar go_router para la navegación.
  • Utilizar flutter_dotenv para configurar la URL base de la API.
  • Aplicar los conceptos de Future, async y await según corresponda.
  • Separar la presentación visual, los modelos y la lógica de comunicación con la API.
  • No realizar peticiones HTTP directamente dentro de los widgets de presentación.
  • Implementar manejo de excepciones y errores de comunicación con Dio.
  • Escribir código organizado, legible y con nombres descriptivos.

6. Despliegue de la API — Opcional (5%)

El despliegue del backend en un servidor es opcional. Pueden desarrollar y ejecutar tanto el backend como Flutter de manera local sin inconveniente.

Quienes deseen obtener el 5% correspondiente al despliegue deberán publicar su API en un servidor o plataforma en la nube, como Railway, Render u otro proveedor de su elección.

Para obtener este porcentaje se deberá demostrar:

  • API accesible públicamente mediante una URL HTTPS.
  • Base de datos funcional y persistente en el entorno desplegado.
  • Aplicación Flutter conectada a la API publicada.
  • Operaciones CRUD funcionando contra el servidor remoto.

Nota: El desarrollo local es completamente válido y permite obtener hasta el 95% de la calificación. El 5% restante se obtiene únicamente cumpliendo los requisitos del despliegue.

7. Repositorio y documentación

Deberan publicar su trabajo en un repositorio de GitHub, incluyendo el código fuente del backend y de Flutter, claramente identificados.

  • Repositorio público que permita revisar ambos proyectos.
  • Uso de Git y commits descriptivos que evidencien el avance.
  • Archivo README.md con descripción general de la solución.
  • Tecnologías utilizadas en el backend y frontend.
  • Instrucciones para instalar y ejecutar ambos proyectos.
  • Descripción de la base de datos y de los endpoints implementados.
  • Ejemplos de peticiones y respuestas JSON de la API.
  • URL pública de la API, si se realizó el despliegue.
  • No incluir contraseñas, credenciales ni secretos en el repositorio.

8. Entregables

8.1. Repositorio GitHub

Entregar el enlace del repositorio público que contenga el backend, la aplicación Flutter y la documentación correspondiente.

8.2. Video explicativo — Obligatorio

Grabar un video donde se explique cómo desarrolló la solución y demuestre su funcionamiento. No será suficiente mostrar únicamente la aplicación terminada.

El video deberá evidenciar:

  1. Backend: explicar la tecnología seleccionada, la base de datos, los endpoints desarrollados y cómo se implementaron las operaciones CRUD.
  2. Pruebas de la API: demostrar las peticiones HTTP utilizando Postman, Thunder Client, Swagger u otra herramienta equivalente.
  3. Flutter: explicar la organización del proyecto, la navegación, el uso de Dio y la forma en que la aplicación se comunica con el backend.
  4. Demostración funcional: mostrar el Dashboard, listado, consulta, registro, edición y eliminación de productos.
  5. Persistencia: demostrar que los registros creados o modificados se conservan en la base de datos.
  6. Despliegue, si aplica: explicar brevemente cómo publicó la API, mostrar la URL pública y demostrar el funcionamiento de Flutter conectado al servidor remoto.

El video deberá tener audio explicativo y permitir observar el código y el funcionamiento real de los proyectos. Puede compartirse mediante un enlace accesible de Google Drive, YouTube (no listado) u otra plataforma.

8.3. PDF de evidencias

El documento PDF deberá contener:

  • Identificación del estudiante.
  • Enlace al repositorio de GitHub.
  • Enlace al video explicativo.
  • Breve descripción de las tecnologías utilizadas.
  • Capturas del Dashboard y de las operaciones CRUD en Flutter.
  • Evidencia de los endpoints y de la base de datos.
  • URL de la API y evidencias del despliegue, si corresponde.
Entrega en Moodle: subir el archivo PDF de evidencias. Los enlaces del repositorio y del video deberán estar incluidos en el documento y contar con permisos de acceso para su revisión.

Criterio Peso Descripción

Dashboard, interfaz y navegación 15% Dashboard con indicadores reales, menú funcional, pantallas organizadas y navegación correcta.

10. Consideraciones finales

  • Se evaluará el funcionamiento real de la solución y la capacidad del estudiante para explicar su implementación.
  • El backend puede ejecutarse localmente o estar desplegado en un servidor.
  • El consumo de la API desde Flutter deberá realizarse mediante Dio.
  • La información debe persistir en una base de datos y mantenerse disponible después de reiniciar la aplicación.
  • La organización del proyecto deberá corresponder a lo desarrollado durante las clases.
  • Los enlaces entregados deberán estar disponibles para su revisión.
